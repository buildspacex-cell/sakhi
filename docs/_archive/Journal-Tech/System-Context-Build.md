System Context — Design, Construction, and Usage
Purpose

System context in Sakhi is the evidence layer supplied to the LLM so that responses are:

grounded in the user’s lived experience

continuous across time

constrained by what is known, not what is guessed

System context is not conversation history and not behavioral instruction.
It is a compact, curated snapshot of truth.

What System Context Is

System context answers one question for the model:

“What do we already know about this person that matters for this response?”

It consists of:

Recalled episodic memory (recent + relevant journals)

Longitudinal patterns (aggregated trends over time)

It does not include:

persona instructions

tone rules

response constraints

identity claims

Those live elsewhere.

High-Level Flow
User journal →
generate_reply →
  build_recall_context
  build_patterns_context
→ system_ctx
→ LLM (with separate instruction system message)
→ response

How System Context Is Built
1. Entry Point: generate_reply(...)

When a journal is submitted, conversation_v2.generate_reply() orchestrates:

recall

pattern summarization

prompt construction

LLM invocation

At this point, no memory is assumed — everything is explicitly fetched.

2. Recall Context (Episodic Grounding)
build_recall_context(person_id, user_text)

What it does

Searches stored episodic memory (journals / episodes)

Computes embedding similarity against the current user text

Ranks results by relevance

Selects top-K memories

Formats them as readable evidence

Output format
Relevant memory:
- [journal] <excerpt> (s=0.47)
- [journal] <excerpt> (s=0.31)

What this provides to the model

Recent lived experience

Emotional and situational continuity

Anchors that prevent hallucinated context

Observed issue (from current runs)

Duplicate memories can appear multiple times

No recency or diversity constraint yet

Similarity alone determines inclusion

3. Patterns Context (Longitudinal Grounding)
build_patterns_context(person_id)

What it does

Reads already-computed aggregates from workers

Summarizes trends over fixed windows (e.g., 7d / 30d)

Does not re-interpret raw journals

Output format
Patterns:
Window 7d:
- general: score=0.00, momentum=0.00
Window 30d:
- general: score=0.00, momentum=0.00

What this provides to the model

Trend awareness

Stability vs change signals

Guardrails against overreacting to single entries

If no signal exists, patterns remain neutral — the model is not asked to invent trends.

4. Concatenation into system_ctx
system_ctx = recall_context + "\n\n" + patterns_context


This combined string is logged and passed forward verbatim.

No tone.
No instructions.
No behavioral rules.

How System Context Is Used by the LLM

Two separate system messages are sent.

System Message 1 — Evidence Window
{
  "role": "system",
  "content": system_ctx
}


Purpose:

Supply facts

Provide continuity

Anchor interpretation

This message answers: what is true?

System Message 2 — Conversational Instructions

Generated by:

build_prompt(user_text, context, tone, metadata)


Includes:

persona mode

tone blueprint

ritual phase

emotional mirroring rules

response length constraints

This message answers: how should Sakhi speak?

User Message
{
  "role": "user",
  "content": user_text
}

Result

The LLM response is conditioned on:

evidence (system_ctx)

behavioral constraints (prompt system message)

the user’s current input

Memory influences grounding, not authority.

Why This Architecture Is Correct

Memory is read-only at generation time

Workers, not the LLM, update state

Evidence is separated from instruction

Longitudinal trends are precomputed, not inferred

The system is observable and debuggable

This makes Sakhi:

safer

calmer

harder to hallucinate

easier to refine

Known Gaps & Improvement TODOs
Recall Context Improvements

 Deduplicate recall results (same memory appearing multiple times)

 Enforce diversity constraints (e.g., max one memory per day)

 Add recency weighting alongside similarity

 Cap total recall tokens deterministically

 Separate “very recent” vs “thematically similar” memories

 Optionally tag recall entries by domain (body / work / emotion)

Patterns Context Improvements

 Expand beyond general domain

 Add confidence scores to pattern summaries

 Suppress pattern blocks when signal strength is below threshold

 Add clear “no signal yet” language instead of zeros

 Make window sizes configurable per environment

System Context Governance

 Define which workers are allowed to feed system context

 Freeze a v1 schema for recall formatting

 Add explicit size limits for system_ctx

 Add debug flag to surface raw recall/pattern inputs in Reflection Lab

 Version system context format (system_ctx_v1)

Reflection Lab Enhancements

 Show recall inputs before formatting

 Toggle recall vs pattern visibility

 Allow re-running recall with different parameters

 Compare system context across runs

 Snapshot system_ctx per turn for auditability

Summary

System context in Sakhi is a curated evidence window built from:

recalled episodic memory

longitudinal pattern summaries

It is injected separately from persona and tone instructions so that:

the model stays grounded in truth

reflection remains human, not reactive

intelligence evolves through workers, not hallucination

Locking this layer cleanly is what allows the rest of the product to scale safely.
